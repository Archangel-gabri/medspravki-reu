# SCENARIOS — прогон вариантов событий ИС МедСправки-РЭУ (QA / доменный анализ)

> Дата: 2026-06-15. Автор: QA/доменный аналитик (Claude).
> База: `docs/PLAN.md` (11 разделов) + `docs/PROJECT-STATUS.md` + **сверка с реальным кодом** в `app/src/`.
> Цель: прогнать разные сценарии (состояния допуска, lifecycle справки, источники черновика, роли,
> edge-кейсы), проверить покрытие доменной моделью/Фазой 0 и найти дыры.

## Что РЕАЛЬНО реализовано (сверено с кодом, не с планом)

Это критично для колонки «Покрыто ли». План описывает гораздо больше, чем собрано. Факты из кода:

- **Сущности есть:** `Student`, `MedicalCertificate`, `Teacher`, `Department`, `StudyGroup`,
  `AuditLog`, `ImportBatch`, `CertificateScan`, Identity (`AppUser`/`AppRole`).
- **Enum есть:** `VerificationStatus(Draft/NeedsReview/Verified/Rejected/Expired/Revoked)`,
  `CertificateStatus(Upcoming/Active/ExpiringSoon/EndsToday/Expired)` — вычисляемый по дате,
  `DraftSource(Manual/ExcelImport/StudentUpload/Ocr)`, `PhysicalEducationGroup(None/Basic/Preparatory/SpecialA/SpecialB/Exempt)`,
  `HealthGroup(I–V/Unknown)`.
- **Сервисы есть:** `RegistryQueryService` (поиск pg_trgm + фильтры + пагинация),
  `StudentService` (создание + дедуп-проверка), `CertificateService.AddAsync`, `IDocumentRecognitionService`
  (Manual + LocalOllama), Scans (загрузка PDF + распознавание).
- **Страницы есть:** Login/Logout, Registry/Index, Students/Create, Students/Details,
  Certificates/Create, BeforeClass/Index, Scans/Index. **Нет:** ReviewQueue, Edit, Audit-журнал (UI),
  Import/Export, личный кабинет студента, дашборд завкафедрой.

### Три системные дыры, которые ломают сразу много сценариев ниже

1. **`VerificationStatus` НИГДЕ не управляет видимостью допуска.** `CertificateService.AddAsync`
   создаёт справку всегда сразу `Verified`. Никаких переходов (NeedsReview→Verified→Rejected/Expired/Revoked)
   в коде нет — это «мёртвый» enum. То есть жизненный цикл кейса (ядро по совету Codex) **в Фазе 0
   объявлен, но не реализован**.
2. **`RegistryQueryService` и `StudentService.GetDetailAsync` выбирают «текущую» справку
   ТОЛЬКО по `EndDate`, игнорируя `VerificationStatus` и `IsDeleted` учитывая, но не статус проверки.**
   → светофор допуска может загореться зелёным от Draft / NeedsReview / Rejected / Revoked справки.
   Это прямое нарушение принципа «официальный факт — только Verified».
3. **`AdmissionStatus` (6-state: NoData/Pending/ClearNormal/ClearWithRestrictions/Exempt/Expired)
   как тип НЕ существует.** В §4 PLAN он заявлен как computed property, но в коде статус допуска
   собирается ad-hoc в `StatusDisplay` из `CertificateStatus` + `PhysicalGroup`. Состояние
   «на проверке» (Pending) вообще не выражается в светофоре реестра.

Дальше «Покрыто ли» оценивается против ЭТОЙ реальности, а не против плана.

Легенда колонки «Покрыто»: ✅ да · 🟡 частично/в плане, нет в коде · ❌ нет ни в модели, ни в коде.

## Ось 2. Жизненный цикл справки (case-lifecycle)

Заявленные переходы: `Draft → NeedsReview → Verified → (Rejected | Expired | Revoked)`.

| # | Переход | Триггер / кто инициирует | Ожидаемое поведение + AuditLog | Экран UI | Покрыто | Дыра/риск |
|---|---|---|---|---|---|---|
| L1 | **(нет) → Draft** | Создан черновик (любой `DraftSource`) | Запись `Draft`, AuditLog `Create` | Создание справки / Scans | 🟡 | Создание есть, но `CertificateService.AddAsync` сразу ставит `Verified`, минуя Draft. Draft как состояние не достижим через UI ручного ввода. |
| L2 | **Draft → NeedsReview** | Преподаватель/студент отправляет на проверку | Смена статуса, попадание в очередь нужного верификатора, AuditLog `Submit(from,to,actor,ts)` | Создание / ReviewQueue | ❌ | Перехода нет в коде. Нет действия «Отправить на проверку». |
| L3 | **NeedsReview → Verified** | MedicalStaff/уполномоченный кликает «Подтвердить» | `VerifiedByUserId/VerifiedAt` ставятся, допуск становится официальным, AuditLog `Approve` | ReviewQueue / Карточка верификации | 🟡 | Поля `VerifiedByUserId/VerifiedAt` есть в сущности и заполняются при ручном вводе, но кнопки/экрана «подтвердить из NeedsReview» нет. |
| L4 | **NeedsReview → Rejected** | Верификатор отклоняет с причиной | `RejectionReason` обязателен, допуск не действует, AuditLog `Reject(+comment)`, уведомление автору | ReviewQueue | 🟡 | Поле `RejectionReason` есть, логики/UI нет. Без обязательности причины — риск немотивированных отказов. |
| L5 | **Verified → Expired** | Фоновый job по `EndDate` (07:00) | `VerificationStatus = Expired`, светофор красный, AuditLog `Expire(system)` | (фон) | ❌ | Джоба нет (Hangfire/Quartz — Фаза 5). Сейчас «истечение» видно только через computed `CertificateStatus`, а `VerificationStatus` остаётся `Verified` навсегда → рассинхрон двух статусов. |
| L6 | **Verified → Revoked** | Admin/HeadOfDepartment аннулирует подтверждённую | Допуск аннулируется немедленно, причина обязательна, INSERT-only AuditLog `Revoke(+reason)` | Карточка / Админ | ❌ | Нет действия Revoke. `Revoked` enum мёртв. Подтверждённую ошибочную/поддельную справку нельзя отозвать. |
| L7 | **Rejected → (повторная отправка)** | Студент исправил и переотправил | Новый кейс или возврат в `NeedsReview`, история отказов сохранена | Кабинет / ReviewQueue | ❌ | Re-submit не моделируется. Неясно: новый кейс или мутация старого. |
| L8 | **Любой → SoftDelete** | Ошибочно созданная справка | `IsDeleted=true`, исключение из реестра, AuditLog `SoftDelete` | Карточка | 🟡 | Поля soft-delete есть; UI-действия и AuditLog-проводки нет. Физудаление запрещено — это правильно. |
| L9 | **Дубль перехода / гонка** | Два верификатора жмут Approve одновременно | Optimistic concurrency (`xmin`) ловит конфликт, второй получает «обновите» | ReviewQueue | 🟡 | `Version`/xmin есть на сущности. На несуществующем переходе не проверено. |

**Вывод по оси 2:** lifecycle описан и типизирован, но это **декларация без реализации**.
В коде есть ровно один путь: создать справку сразу `Verified`. Ни одного перехода, ни AuditLog-проводки
переходов, ни очереди. Для Фазы 2 это центральный недострой.

## ТОП-критичные дыры (что модель НЕ покрывает — чинить в первую очередь)

Ранжировано по риску (доверие/право/безопасность × частота).

1. **Светофор допуска не фильтрует по `VerificationStatus`.** (A2, L-весь, E2)
   Реестр/карточка берут последнюю справку по `EndDate` без учёта статуса проверки и без понятия
   «активная Verified». → Draft/NeedsReview/Rejected/Revoked справка может показать зелёный «Действует».
   **Это подрывает само ядро системы** («официальный факт — только Verified»). Чинить: ввести computed
   `AdmissionStatus` поверх **только** `Verified && StartDate ≤ today ≤ EndDate && !IsDeleted`, и состояние
   `Pending` для NeedsReview.

2. **Жизненный цикл кейса — декларация без реализации.** (Ось 2 целиком)
   Enum `VerificationStatus` есть, но в коде только один путь `Manual → Verified`. Нет ни одного перехода,
   ни ReviewQueue, ни Revoke, ни Expire-job, ни AuditLog-проводок переходов. Ядро по совету Codex (§11.1)
   на бумаге. Для Фазы 2 это центральная работа.

3. **Нет `Revoke` подтверждённой справки.** (L6, E12)
   Ошибочно/поддельно подтверждённую справку нельзя штатно отозвать с причиной и историей. Для медданных
   и анти-фрода это обязательная операция, а не «потом».

4. **Нет временного освобождения (095/у) поверх постоянной физгруппы.** (E5)
   `TemporaryExemption` сущности нет. Сейчас освобождение = перезапись `PhysicalGroup=Exempt`, что стирает
   Preparatory/SpecialA и не откатывается после окончания 095/у. Частый реальный кейс кафедры.

5. **Принудительное разграничение доступа по ролям не внедрено.** (R1, R3, R6)
   `TeacherId` — лишь необязательный фильтр в реестре, не EF `HasQueryFilter` по `IUserContext`.
   Физрук технически видит чужих студентов и потенциально скан/медполя → нарушение минимизации
   152-ФЗ/323-ФЗ. Совмещение ролей (физрук+MedicalStaff) обходит минимизацию.

6. **Перекрывающиеся / частично покрывающие справки + будущий StartDate.** (E4, E8)
   «Активная» = `OrderByDescending(EndDate).First()` без правила приоритета и без проверки перекрытий;
   `current` считается по `EndDate >= today`, игнорируя `StartDate > today` → справка «из будущего»
   показывается как текущая. Нужна детерминированная выборка активной + предупреждение о перекрытии.

7. **Нет дискриминатора формы документа (086/у vs 211н).** (E11)
   Невозможно применять разные правила к формам и корректно объяснять источник физгруппы/группы здоровья.

8. **UnassignedQueue не существует.** (E10)
   Студент без `TeacherId` выпадает из всех отфильтрованных списков и теряется — нет экрана/выборки
   «без физрука» для завкафедрой.

9. **Дедуп студентов хрупкий.** (E3)
   Ключ `ФИО+группа`: тёзки в группе → ложный дубль; перевод в другую группу → дубль не ловится;
   при импорте (которого пока нет) дедупа не будет вовсе. Нужен устойчивый идентификатор
   (студбилет/дата рождения) — пересекается с блокирующим вопросом §9.2-bis (доверенная идентификация).

10. **Нет фоновых переходов и уведомлений (Expire/ExpiringSoon-engine).** (A6/A7, E1, L5)
    `VerificationStatus` не переводится в `Expired` — два статуса (date-based и lifecycle) расходятся
    навсегда. Истечение в середине семестра проходит «тихо».

11. **ФЗ-273 запрет авто-оценок не закреплён в модели.** (E9)
    Advisory-бейдж/лог показа отсутствуют; нет структурного запрета, который не даст будущему разработчику
    случайно завязать оценку на допуск. Нужен явный advisory-only тип + лог `RestrictionBadgeShown`.

12. **Источники Excel/OCR не доходят до кейса.** (S2, S4, S5)
    `ImportBatch` есть, импорта нет; OCR распознаёт, но «применить → создать справку» не реализовано;
    связки «правка поверх OCR → training sample» нет. DraftSource-абстракция пока работает только для Manual.

### Что в модели сделано ПРАВИЛЬНО (не трогать)

- Разделение `CertificateStatus` (по сроку, computed) и `VerificationStatus` (доверие к кейсу) — верно.
- `DraftSource` как ось, ортогональная lifecycle — верный фундамент (когда переходы реализуют).
- Минимизация ПДн: `Restrictions` без диагноза, скан вне wwwroot + SHA-256, soft-delete вместо физического.
- Светофор всегда дублируется текстом (дальтоники), severity-сортировка «Перед парой».
- `Manual → Verified` для ручного ввода уполномоченным — корректная семантика ТЗ v1.
