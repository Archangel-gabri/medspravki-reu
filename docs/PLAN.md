# PLAN — ИС учёта медицинских справок кафедры физкультуры РЭУ им. Плеханова

> Проект: `MedSpravki-REU`. Рабочий код — `app/`.
> Статус: **каркас плана** (v2-расширение поверх действующего ТЗ v1 manual-варианта).
> Главное предостережение из критики: официальное ТЗ v2 ещё не пришло («в течение недели»), действующее ТЗ v1 **прямо исключает** загрузку студентами/сканы/OCR (разделы 5.2, 31). Этот план — упреждающий roadmap, а не санкция начинать v2-код. Резать агрессивно, сначала закрыть v1, не писать v2 до подписи ТЗ и ответов на блокирующие вопросы (§9).

## 1. Видение и реальная ценность

**Что меняем.** Бумажная картотека справок → живой реестр допусков, где статус «есть ли действующая справка и какие ограничения» виден за секунду. Это не «весёлый SaaS», а защищённый реестр персональных медданных вуза.

- **Студент** (v2, после подтверждения сетевого доступа): из бумажной беготни «принести справку лично» → сфотографировал в телефоне → ИИ предзаполнил поля → отправил → видит статус-светофор «Допуск действует до 15.09.2026 / На проверке / Нет справки / Истекает». Ноль медтерминов, одна кнопка действия.
- **Физрук** (ценность уже в v1): перед парой открывает «Список группы на сегодня» → светофор по каждому студенту (зелёный/жёлтый/красный/серый), физкультурная группа, ограничения, срок. Студенты без действующей справки — сверху и красным. Видит **только** агрегированный допуск, **не** скан и **не** диагноз (152-ФЗ/323-ФЗ).
- **Кафедра / зав. кафедрой**: дашборд по 9 факультетам, доля студентов с актуальными справками, аудит всех действий, экспорт в Excel. Контроль учебного процесса, а не передача его алгоритму.

**Граница честности с заказчиком (закрыть до демо):** «ИИ распознаёт печати и группу здоровья» = реально 40–75% на рукописных полях, обязательная ручная проверка каждого медполя; «проверка подлинности» = только сигнал о подозрительности, не гарантия. «Корректировка оценок» = advisory-подсказка физруку, **не** авто-выставление (ФЗ-273).

**Ранняя ценность:** компилируемый v1-реестр (без ИИ, без сканов, ввод преподавателем) уже полностью заменяет бумагу, и кафедра начинает им пользоваться задолго до v2.

## 3. Honest take: главный конфликт и как его развязать

### Конфликт A — офлайн-периметр vs облачный/сетевой ИИ (фундаментальный)
ТЗ описывает машину кафедры в ЛВС, «интернет необязателен», «флешка/сетевая папка». Но «студент сам загружает справку», PWA, email @rea.ru, Telegram, Yandex Vision — **все требуют сетевой доступности, которой в этом сценарии нет**. Студент физически не подключён к машине кафедры.
→ **Развязка:** это не архитектурная, а **организационная** развилка — блокирующий вопрос заказчику (§9). До ответа загрузка студентом и уведомления **вырезаны из MVP**; данные вносит преподаватель (как требует действующее ТЗ).

### Конфликт B — медПДн vs 152-ФЗ (US-облака запрещены, Yandex — с оговорками)
Данные из 086/у — спецкатегория (ст. 10 152-ФЗ) + врачебная тайна (ст. 13 323-ФЗ). OpenAI/Gemini/Claude (US-юрисдикция) — **недопустимы** для медПДн. Даже Yandex Vision (РФ, ФСТЭК) требует письменного согласия на конкретного получателя и противоречит изолированному периметру.
→ **Развязка архитектурно — pluggable провайдер распознавания:**

```
interface IDocumentRecognitionService {
    Task<RecognitionResult> RecognizeAsync(ScanInput scan, CancellationToken ct);
}
```
Реализации в Infrastructure, выбор через config (`Recognition:Provider = Manual | Local | Yandex`):
- **ManualProvider** (ДЕФОЛТ и единственный в MVP): всегда `null` + `RequiresManualReview=true`. Система обязана работать **без GPU и без Python вовсе**.
- **LocalProvider** (фаза ИИ-ассист): HTTP к локальному Python-микросервису (Tesseract/PaddleOCR + Ollama Qwen2.5-VL на ПК кафедры). Всё в периметре РЭУ — 152-ФЗ закрыт из коробки.
- **YandexProvider** (опционально, только при письменном согласии РЭУ-оператора): РФ-юрисдикция, ФСТЭК.

Переключение облако/локально/ручной **не трогает домен** (Clean Architecture). Это разрешает оба внутренних противоречия исследования («не хранить сканы» vs «шифрованное хранилище») — см. §7.

### Human-in-the-loop как основа доверия (не best-practice, а обязательный элемент)
Точность на рукописных полях 086/у — 40–75%; 25–40% документов требуют ручной правки минимум одного поля. Поэтому:
- статус **`Approved` ставит ТОЛЬКО человек** кликом; ИИ лишь предзаполняет черновик;
- поля «Группа здоровья» и «Ограничения» требуют ручного подтверждения **всегда**, независимо от confidence (медицинская ответственность);
- в карточке фиксируется «Проверено [ФИО] [дата]»; каждое исправление → training sample под будущий LoRA fine-tuning.
ИИ **никогда** не конечный источник медрешения. В UI явно: «Система не подтверждает подлинность справки».

## 4. Целевая модель

### Роли (в MVP — одна `Teacher`; таблицы users/roles готовы под расширение)
| Роль | Видит | Может |
|---|---|---|
| **Student** (v2) | свою карточку, статус, сроки | загрузить справку, подтвердить распознанное (не присвоить допуск) |
| **Teacher** (физрук) | своих студентов: физкультурную группу + ограничения + статус + срок. **НЕ** скан, **НЕ** диагноз | вести реестр, Approve агрегированного допуска своих студентов |
| **MedicalStaff** (верификатор медполей) | полный медпрофиль + скан | верифицировать медполя, видеть скан |
| **HeadOfDepartment** (зав. кафедрой) | все справки кафедры, дашборд по 9 факультетам | всё + переназначение |
| **Admin** | техоперации | Revoke, импорт, роли |

Разделение доступа — на уровне **EF Core query filters по роли** (`HasQueryFilter` + `IUserContext`), не на фронте (иначе обходится).
⚠️ Открытый вопрос: на кафедре физкультуры медработника может не быть в штате — кто легитимно играет `MedicalStaff` (§9).

### Статусы СПРАВКИ (`MedicalCertificate.VerificationStatus`)
`Draft → Submitted → AiProcessed → UnderReview → Approved | Rejected → Expired | Revoked`
Каждый переход → запись в `AuditLog(from, to, actor, ts, comment)`.

### Статус ДОПУСКА студента (`AdmissionStatus`) — **computed property, НЕ хранимое поле**
`NoData | PendingCertificate | ClearNormal | ClearWithRestrictions | Exempt | ExpiredCertificate`
Вычисляется из активной справки на лету (нет рассинхронизации). Фоновый job (фаза уведомлений) переводит `Approved → ExpiringSoon → Expired` по `EndDate`.

### Два РАЗНЫХ классификатора (критично для модели БД — не путать)
- **Группа здоровья** (I–V) — общая медоценка, опционально, медполе.
- **Физкультурная группа** (Основная / Подготовительная / Спец. «А» / Спец. «Б», по приказу 211н с 01.09.2025) — определяет практику, основное поле для физрука.
Поддержать обе формы документа: 086/у (действуют до истечения) + Медзаключение 211н.

### Маршрутизация к физруку
`Student.TeacherId` (из импорта Excel деканата или выбор студентом при первом входе). При отправке справки `TeacherId` копируется в очередь. Физрук видит только items где `AssignedTeacherId == его`. `TeacherId is null` → `UnassignedQueue`, видимая `HeadOfDepartment`. Реассигнация → AuditLog.

### Оценки — ТОЛЬКО подсказка (advisory)
**Никакого авто-выставления** (ФЗ-273, оценка = академический акт за подписью преподавателя). Физруку показывается бейдж ограничений + «рекомендуемый режим/диапазон»; для `Exempt` система форсирует выбор «зачёт по иному основанию», но финальный выбор за преподавателем. Показ бейджа логируется в аудит (`RestrictionBadgeShown`).

### Временное освобождение
`TemporaryExemption` (1:N к студенту, 095/у/027/у): флаг «освобождён до ДД.ММ» перед парой. Не путать с постоянной физкультурной группой.

## 5. Стек-решение

**Оставляем выбранный стек без переписывания** — все цели v2 реализуемы в нём:
ASP.NET Core 8 + Razor Pages + HTMX + Bootstrap 5.3 + PostgreSQL 16 (pg_trgm) + EF Core 8 + ASP.NET Identity + ClosedXML + Serilog. Clean Architecture (Domain/Application/Infrastructure/Web). Развёртывание: IIS на Windows в ЛВС РЭУ → локализация ПДн (ст. 18.1 152-ФЗ) выполняется автоматически.

**Где живёт ИИ-сервис.** Отдельный **Python-микросервис FastAPI** на `127.0.0.1:8000` (или LAN-адрес ПК с GPU), вызывается из .NET через `HttpClient` из фонового джоба. Это:
- изолирует тяжёлые Python-зависимости (PaddleOCR/Ollama) от .NET-стека;
- держит pluggable local/cloud за единым `IDocumentRecognitionService` (§3);
- **опционален** — система полностью работает без него (ManualProvider).
В самом первом ИИ-MVP допустим вызов через `Process.Start` без FastAPI; FastAPI — production-слой позже.

**Дефолт распознавания:** локальный офлайн (Tesseract/PaddleOCR + Ollama Qwen2.5-VL 7B Q4_K_M, ~5–6 ГБ VRAM, влезает в RTX 3060 12 ГБ). Облачные US-API — **только** для разработки/тестов на синтетических/обезличенных данных.

**Хранение:** сканы — в файловом хранилище **вне wwwroot** (не bytea в БД), путь+SHA-256+метаданные в PostgreSQL. В MVP сканы **не хранятся вообще** (§7).

## 6. Дорожная карта фазами (с честными MVP-границами)

> Принцип: после каждой фазы — рабочий результат. Сначала закрыть v1, v2 — аддитивно и по одной фиче **только после подписи ТЗ v2**.

### Фаза 0 — Починить скаффолд до компилируемого v1 (БЕЗ AI, БЕЗ сканов, одна роль)
**Это и есть действующее ТЗ. Безрисковая инвестиция, нужная при любом будущем v2.**
- Реализовать 9 сущностей v1 (User/Role/Department/Teacher/StudyGroup/Student/MedicalCertificate/AuditLog/ImportBatch) + enum + EF Core миграции.
- **Убрать из `Program.cs`/`DependencyInjection.cs` всё про student-portal/registration/SeedIdentity**, пока роль студента не утверждена.
- Реестр с поиском (GIN/pg_trgm) + фильтры, CRUD студентов/справок, optimistic concurrency (`Version`).
- Импорт/экспорт ClosedXML, AuditLog, computed-статус справки.
- Сидинг 9 факультетов + ~13 физруков.
- **Выход:** зелёный билд + проходящий тест `MedicalCertificate` статуса = честная Фаза 0. Полная замена бумаги.

### Фаза 1 — Дашборд физрука «Перед парой» + светофор (всё ещё v1-данные)
- Дашборд «Список группы на сегодня»: ФИО · группа · физкультурная группа · ограничения · статус · истекает; цветовые бейджи (зелёный/жёлтый/красный/серый), дублируются текстом+иконкой.
- Фильтр по коду группы. Экспорт Excel. Реестр master-detail по вайрфрейму.
- **Выход:** физрук получает ежедневную ценность без единой строки ИИ-кода.

### Фаза 2 — [после подписи ТЗ v2 + ответа про сетевой доступ] Статусная модель + ручная верификация
- Роли поверх Identity (таблицы готовы с Фазы 0), `IDocumentRecognitionService` с **ManualProvider-заглушкой**.
- `VerificationStatus` enum + переходы + AuditLog. ReviewQueue + маршрутизация к физруку (resource-based authorization).
- UI верификации (ручной ввод полей, без AI). `TemporaryExemption`.
- **Сканы пока НЕ храним** — только результат верификации.
- **Выход:** полный workflow submit → manual-review → approve без AI и без сканов.

### Фаза 3 — Личный кабинет студента + загрузка (только если подтверждён сетевой доступ + согласие ПДн оформлено)
- StudentPortal: регистрация по @rea.ru, своя карточка, статус-плитка, PdnConsent (блокирует загрузку без согласия).
- Приём JPEG/PNG/PDF ≤10 МБ; **хранение сканов** — только если РЭУ-оператор оформил согласия + приказ + Модель угроз ФСТЭК + уведомление РКН (иначе остаёмся на ручном вводе результата).
- `IScanStorageService`: шифрованное хранилище вне wwwroot, GUID-имена, SHA-256, авторизованный download-endpoint (только MedicalStaff/Admin/HeadOfDepartment).

### Фаза 4 — ИИ-ассист (human-in-the-loop, дефолт = локальный провайдер)
- `LocalProvider` (FastAPI) — **OCR-first конвейер** (уточнение Codex, §11): предобработка (deskew/contrast/300 DPI) → PaddleOCR/Tesseract(rus) → **regex/rules для дат, срока, кода группы, ФИО-кандидатов** → локальный VLM (Qwen2.5-VL 7B Q4) **только для неоднозначностей**, а не «VLM читает всё» → per-field confidence → детекция печати/подписи (наличие, не подлинность).
- `OcrExtractionResult` (поля + per-field confidence + raw JSON). UI: скан слева, поля справа, подсветка `<0.85` жёлтым; медполя — всегда ручное подтверждение.
- Каждое исправление → training sample под будущий fine-tuning. ИИ **никогда** не источник истины — только черновик-источник для `VerificationDecision` (§11).

### Фаза 5 — Уведомления, expiry-engine, анти-фрод, advisory-оценка
- Hangfire/Quartz: ежедневно 07:00 `Approved→ExpiringSoon→Expired`; напоминания студенту (30/7 дней, email @rea.ru + in-app bell); digest физруку; отчёт зав. кафедрой. French PAPS: авто-задача загрузить справку при добавлении в группу.
- Анти-фрод как **risk_score 0..1** (advisory, не бинарный): в MVP только **логическая валидация** в .NET (дата ≤ сегодня, срок, группа из перечня, Levenshtein ФИО vs профиль); ELA/EXIF/clone/font-микросервис — последняя, низкоприоритетная фаза (риск иллюзии безопасности).
- `GradeAdjustmentNote` (advisory-бейдж + лог показа). INSERT-only AuditLog (revoke GRANT UPDATE/DELETE + триггер). Telegram — опционально v2-late.

**Что вырезано из MVP (scope cuts):** весь AI/OCR-конвейер, анти-фрод-микросервис, хранение сканов, загрузка студентом/личный кабинет, email/Telegram/expiry-job, сложная ролевая модель (оставить одну `Teacher` + готовые таблицы), advisory-оценка, PWA/cropperjs, Yandex Vision. Всё — поздние аддитивные фазы.

## 7. ПДн / 152-ФЗ и безопасность — обязательный чеклист

- [ ] **Минимизация (ст. 5):** НЕ хранить диагноз в ИС кафедры физкультуры. Только физкультурная группа + ограничения (функциональные формулировки, без диагноза) + метаданные справки. `Diagnosis` либо отсутствует, либо доступен исключительно `MedicalStaff`.
- [ ] **Сканы в MVP — НЕ хранить вообще** (снимает ~80% юрриска, совпадает с ТЗ v1). Если хранение нужно — только режим: шифрованно вне wwwroot, AES-256 at-rest, SHA-256 (пересчёт при открытии = анти-подмена), download только для MedicalStaff/Admin, `PurgeAfter` после верификации.
- [ ] **Разделение доступа на уровне EF Core query filters** (не фронта): физрук не видит скан/диагноз/МО — требование ст. 10/19 152-ФЗ + ст. 13 323-ФЗ.
- [ ] **Письменное согласие на спецкатегорию (ст. 10 ч. 2 п. 1)** для каждого студента ДО обработки медданных. `PdnConsent` фиксирует факт+дату+форму. Форму разрабатывает юрслужба РЭУ. Без согласия — штраф ст. 13.11 КоАП 60–300 тыс. (повтор до 500 тыс.); оператор = РЭУ.
- [ ] **Локализация в РФ (ст. 18.1):** БД + хранилище + бэкапы физически в РФ. ЛВС РЭУ/IIS выполняет автоматически. ЗАПРЕТ Google/AWS/Azure/OpenAI/Gemini/Claude для медданных.
- [ ] **УЗ-3 по ПП РФ 1119** (спецкатегория, <100k субъектов): ответственный за обработку (приказ по вузу), Модель угроз ФСТЭК, уведомление РКН как оператора (ст. 22), сертифицированные СЗИ, физзащита серверной, журналирование доступа к медполям, проверка СЗИ раз в 3 года. **Орг-меры на стороне РЭУ** — без них прод незаконен.

## 11. Второе мнение Codex (GPT-5.5, xhigh) — подтверждения и уточнения плана

Полный ответ: `sessions/handoff/outgoing/think-20260614-202507.md`. Codex независимо **подтвердил стратегию** «сначала v1, заморозить v2 до подписи ТЗ» (ИИ-прототип — только учебный spike, не продуктовая ставка) и **подтвердил**, что Qwen2.5-VL 7B на RTX 3060 запустить реально, но **надёжного production-экстрактора российских медсправок из него не выйдет** — «ИИ может предзаполнять черновик и экономить время верификатора, но не является источником истины». Шесть уточнений, которые приняты в план:

1. **АРХИТЕКТУРНЫЙ ГЛАВНЫЙ СОВЕТ — моделировать жизненный цикл КЕЙСА справки, а не «ручной v1 vs ИИ v2».**
   `Draft → NeedsReview → Verified → (Rejected | Expired | Revoked/Corrected)`.
   Тогда ручной ввод, импорт Excel, будущая загрузка студентом и OCR — это просто **разные ИСТОЧНИКИ черновика** (`DraftSource = Manual | ExcelImport | StudentUpload | Ocr`), а официальным фактом остаётся только `VerificationDecision`, подтверждённый человеком. Это устраняет переписывание архитектуры под v2 — заменяет более частную модель статусов из §4 и делает её источник-агностичной. **Принять как ядро доменной модели уже в Фазе 0.**
2. **Честность по юрриску: v1 ≠ «почти без риска».** Даже без сканов физкультурная группа, ограничения и сроки справки — медицински значимые ПДн. Формулировку §1/§7 «снимает ~80% юрриска» понимать как «снимает риск, связанный со *сканами и диагнозом*», но сам реестр всё равно требует согласия, минимизации и защиты. Не продавать кафедре как «безопасно».
3. **Узкое место личного кабинета — не форма загрузки, а ИДЕНТИФИКАЦИЯ студента.** SSO/AD/ЛК РЭУ, доверенная привязка студент↔группа↔физрук. Без неё автозагрузка = источник мусора. → добавлен блокирующий вопрос: как студент аутентифицируется и как доверенно привязывается к группе (есть ли AD/SSO/выгрузка деканата).
4. **«Сетевая папка / флешка» — это НЕ план развёртывания** для IIS+PostgreSQL. Нужны: установочный runbook, миграции, backup/restore, шаблон `appsettings.Production.json`, bootstrap-admin, офлайн-артефакты (NuGet/runtime). → **deployment-runbook становится отдельным deliverable Фазы 0**, а не сноской.
5. **Импорт/экспорт Excel, вероятно, даёт больше реальной пользы, чем OCR** — и его нельзя делать как мелкую утилиту: dry-run, ошибки по строкам, дедупликация, аудит импорта (`ImportBatch` уже в модели). Поднять приоритет качества импорта в Фазе 0.
6. **Одна роль `Teacher` может быть слабовата уже для v1:** завкафедрой/админ кафедры, физрук-по-своим-группам, read-only/аудитор, техадмин — разные права. → в Фазе 0 заложить **минимум `Teacher` + `HeadOfDepartment` + `Admin`** (таблицы ролей и так есть), не откладывая всё разграничение на v2.

**Где Claude и Codex полностью согласны:** v1-first; ИИ — необязательная поздняя фаза за `IDocumentRecognitionService`/ManualProvider; локальный офлайн-ИИ вместо US-облака; human-in-the-loop обязателен; авто-оценки запрещены (ФЗ-273); анти-фрод «подлинности» — иллюзия, вырезать. **Расхождение только в акцентах:** Codex жёстче настаивает, что (а) v1 тоже юр-чувствителен и (б) ИИ должен быть OCR+правила-first, а VLM — лишь для неоднозначностей (а не VLM-primary, как было в §5). Оба уточнения приняты.
