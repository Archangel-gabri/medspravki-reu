# Подробное техническое задание и архитектурная спецификация

## на разработку локальной системы учета медицинских справок студентов кафедры физической культуры РЭУ

Версия: `1.0`  
Дата: `29.04.2026`

## 1. Статус документа

Настоящий документ является рабочим техническим заданием для проектирования и разработки системы.  
Разработка системы должна вестись по данному документу как по основному техническому ТЗ второй детализации.

## 2. Краткое описание задачи

Кафедре физической культуры требуется единая локальная информационная система, в которой преподаватели смогут:

- авторизоваться под своим логином и паролем;
- видеть общий реестр студентов и медицинских справок;
- быстро искать студента по ФИО;
- фильтровать записи по учебному подразделению, курсу, группе, преподавателю и статусу;
- добавлять и редактировать справки;
- видеть сроки действия справок и ограничения;
- работать с историей прошлых справок;
- просматривать журнал изменений.

Система должна заменить текущий бумажный процесс, при котором данные могут теряться, быть распределены между разными преподавателями и долго искаться вручную.

## 3. Принятые технические допущения

Для исключения неоднозначности в проектировании в рамках данного ТЗ принимаются следующие решения:

- первая версия системы реализуется как `локальное веб-приложение`, а не desktop-приложение;
- доступ к системе осуществляется из внутренней сети университета;
- в первой версии сканы справок не хранятся;
- данные со справок вносятся преподавателем вручную;
- основная роль в системе одна: `преподаватель`;
- все преподаватели имеют одинаковый уровень доступа к данным;
- в системе используется централизованная база данных;
- система разрабатывается как `модульный монолит`, а не как набор микросервисов.

## 4. Выбранный стек технологий

### 4.1. Общий подход

Для первой версии выбирается стек, ориентированный на:

- надежную работу в локальной сети;
- простое развертывание на Windows-инфраструктуре;
- минимальное количество внешних зависимостей;
- высокую поддерживаемость;
- простую реализацию административного интерфейса.

### 4.2. Конкретный стек

#### Backend

- `C# / .NET 8`
- `ASP.NET Core 8`
- `Razor Pages` как основа интерфейса
- `ASP.NET Core Identity` для аутентификации
- `Entity Framework Core 8` для доступа к БД
- `FluentValidation` для серверной валидации
- `Serilog` для журналирования

#### Frontend

- `Razor Pages` с серверным рендерингом
- `Bootstrap 5.3` для базовой сетки, таблиц и форм
- `HTMX` для частичных обновлений таблиц и форм без полной перезагрузки страницы
- `Vanilla JavaScript` для точечной клиентской логики

#### База данных

- `PostgreSQL 16`
- `Npgsql` как провайдер PostgreSQL для .NET
- расширение `pg_trgm` для быстрого частичного поиска по ФИО

#### Excel

- `ClosedXML` для импорта и экспорта файлов Excel формата `.xlsx`

#### Тестирование

- `xUnit`
- `FluentAssertions`
- `Microsoft.AspNetCore.Mvc.Testing`
- `Playwright` для smoke-тестов ключевых экранов

#### Развертывание

- `Windows 10/11 Pro` либо `Windows Server`
- `IIS` как reverse proxy и точка публикации
- приложение ASP.NET Core запускается как серверный процесс за IIS
- PostgreSQL разворачивается как отдельная служба на том же сервере или на выделенной внутренней машине

## 5. Почему выбран именно этот стек

- `ASP.NET Core` хорошо подходит для внутренней административной системы на Windows-инфраструктуре.
- `Razor Pages` проще и надежнее для подобного бизнес-приложения, чем SPA на React/Vue, потому что здесь важнее стабильные формы, таблицы и фильтры, а не сложный клиентский интерфейс.
- `PostgreSQL` надежнее и масштабируемее, чем SQLite, при одновременной работе нескольких пользователей.
- `HTMX` позволяет оставить интерфейс простым, но при этом сделать быстрый поиск, фильтры и модальные формы без тяжёлого фронтенд-фреймворка.
- `ClosedXML` покрывает задачи импорта и экспорта Excel без сложной интеграции с Microsoft Office.

## 6. Архитектурный стиль

Система разрабатывается как `модульный монолит`.

Это означает:

- одно веб-приложение;
- одна общая база данных;
- логика разделена на слои и модули;
- отсутствуют отдельные микросервисы;
- развертывание происходит как одного приложения.

Такой подход выбран потому, что:

- система предметно небольшая;
- требуется быстрый запуск и простая поддержка;
- микросервисная архитектура здесь создаст ненужную сложность.

## 8. Физическая схема работы системы

Система под капотом должна работать следующим образом:

1. Пользователь на компьютере университета открывает браузер.
2. В браузере открывается внутренний адрес системы, например `http://medspravki-reu`.
3. Запрос попадает в `IIS`.
4. `IIS` передает запрос в приложение `ASP.NET Core`.
5. Приложение проверяет авторизацию пользователя по cookie-сессии.
6. При необходимости приложение обращается к `PostgreSQL`.
7. Данные обрабатываются на сервере.
8. Пользователю возвращается HTML-страница либо частичное обновление фрагмента интерфейса.
9. Все важные операции фиксируются в журнале изменений и технических логах.

## 12. Бизнес-логика и правила работы

### 12.1. Правила по студентам

- При создании студента система должна проверять возможный дубль по `NormalizedFullName + StudyGroupId`.
- Если найдено совпадение, система должна показать предупреждение и предложить открыть существующую карточку.
- Студент может быть деактивирован, но не удален физически.

### 12.2. Правила по справкам

- У одного студента может быть несколько справок.
- Справки с пересекающимися периодами допустимы только после явного подтверждения пользователя.
- Справка с `EndDate < StartDate` сохраняться не должна.
- При удалении справки выставляется `IsDeleted = true`.
- Все действия по справке пишутся в аудит.

### 12.3. Правила по журналу изменений

Фиксируются:

- создание студента;
- изменение студента;
- создание справки;
- изменение справки;
- логическое удаление справки;
- импорт данных;
- вход в систему и неуспешная попытка входа по техническому логу.

### 12.4. Правила по статусам справки

Статус вычисляется на лету:

- `Active`, если `CurrentDate >= StartDate` и `CurrentDate <= EndDate`
- `Expired`, если `CurrentDate > EndDate`
- `Upcoming`, если `CurrentDate < StartDate`
- `ExpiringSoon`, если `EndDate - CurrentDate <= ExpiringSoonThresholdDays` и справка еще не истекла

Значение `ExpiringSoonThresholdDays` должно настраиваться в конфигурации, по умолчанию `7`.

## 13. Поиск и фильтрация

### 13.1. Поиск по ФИО

Поиск по ФИО должен:

- поддерживать частичный ввод;
- работать без учета регистра;
- корректно искать по русскоязычным данным;
- давать быстрый отклик на типовых объемах данных.

### 13.2. Реализация под капотом

Для этого в PostgreSQL должно использоваться:

- поле `NormalizedFullName`;
- расширение `pg_trgm`;
- индекс `GIN` по `NormalizedFullName`.

Примерная стратегия:

- строка поиска нормализуется;
- выполняется запрос по `ILIKE` либо триграммному совпадению;
- результаты сортируются по точности и ФИО.

### 13.3. Фильтры

Система должна поддерживать фильтры:

- подразделение;
- курс;
- группа;
- преподаватель;
- статус справки;
- период окончания справки.

## 14. Импорт Excel

### 14.1. Поддерживаемый формат

Первая версия поддерживает `xlsx`.

### 14.2. Ожидаемые колонки

Минимально ожидаются:

- `ФИО`
- `Подразделение`
- `Курс`
- `Группа`
- `Преподаватель`

Дополнительные поля могут быть добавлены позже после согласования шаблона.

### 14.3. Сценарий импорта

1. Пользователь открывает экран импорта.
2. Загружает Excel-файл.
3. Система проверяет расширение и базовую структуру.
4. Система считывает строки.
5. Система валидирует каждую строку.
6. Система строит предварительный отчет:
   - сколько новых студентов будет добавлено;
   - сколько существующих будет обновлено;
   - сколько строк содержит ошибки;
   - какие строки пропущены.
7. После подтверждения выполняется сохранение.
8. Результат импорта сохраняется в `ImportBatch`.

### 14.4. Правила импорта

- Импорт не удаляет существующие справки.
- Импорт обновляет справочные данные и карточки студентов.
- Импорт не должен silently перетирать критические поля без аудита.
- Все изменения, внесенные импортом, должны быть отражены в журнале.

## 15. Экспорт Excel

### 15.1. Назначение

Экспорт используется для выгрузки результата фильтрации и поиска.

### 15.2. Формат

- `xlsx`

### 15.3. Состав данных экспорта

В файл должны попадать:

- ФИО;
- подразделение;
- курс;
- группа;
- преподаватель;
- группа здоровья;
- физическая группа;
- ограничения;
- дата начала;
- дата окончания;
- статус.

### 15.4. Под капотом

- экспорт формируется сервером;
- данные берутся из текущего набора фильтров;
- файл генерируется во временной памяти без сохранения на диск, если не требуется иное;
- пользователю возвращается потоковый ответ на скачивание.

## 19. Параллельное редактирование и защита от конфликтов

Так как все преподаватели имеют одинаковые права редактирования, в системе нужно предусмотреть защиту от перезаписи данных.

Выбранный механизм:

- optimistic concurrency;
- у сущностей `Student` и `MedicalCertificate` хранится поле `Version`;
- при сохранении проверяется, не менялась ли запись после открытия формы;
- если запись уже изменена другим пользователем, система показывает сообщение:
  - кто изменил запись;
  - когда это произошло;
  - предлагает перезагрузить данные и повторить изменение.

## 20. Аутентификация и безопасность

### 20.1. Аутентификация

Используется `cookie-based authentication` на базе `ASP.NET Core Identity`.

### 20.2. Пароли

- хранятся только в виде хэша;
- открытый пароль в БД не хранится;
- политика минимальной длины задается конфигурацией.

### 20.3. Сессии

- пользователь после успешного входа получает защищенную cookie;
- время жизни сессии настраивается;
- неактивные сессии истекают автоматически.

### 20.4. Защита приложения

Должны быть включены:

- `HTTPS`, если инфраструктура университета это позволяет;
- `AntiForgery` для POST-форм;
- защита от массовых неуспешных попыток входа;
- журналирование ошибок входа;
- запрет доступа к страницам без авторизации.

## 21. Техническое журналирование

## 28. Сценарии использования

### 28.1. Добавление нового студента и справки

1. Пользователь открывает реестр.
2. Нажимает кнопку добавления студента.
3. Заполняет карточку студента.
4. Система проверяет дубли.
5. Пользователь сохраняет студента.
6. Открывает форму новой справки.
7. Заполняет даты, ограничения, группы здоровья.
8. Система валидирует данные.
9. Справка сохраняется.
10. Создается запись в журнале изменений.

### 28.2. Поиск студента

1. Пользователь вводит часть ФИО.
2. HTMX отправляет запрос на сервер.
3. Сервер выполняет поиск в PostgreSQL.
4. Возвращается обновленный фрагмент таблицы.

### 28.3. Импорт Excel

1. Пользователь открывает экран импорта.
2. Загружает файл.
3. Сервер читает файл через ClosedXML.
4. Строки валидируются.
5. Показывается предварительный отчет.
6. После подтверждения данные сохраняются в БД.
7. Формируется итоговый отчет.
