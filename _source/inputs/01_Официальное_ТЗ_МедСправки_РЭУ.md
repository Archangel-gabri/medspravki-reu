# Техническое задание

## на разработку локальной информационной системы учета медицинских справок студентов кафедры физической культуры РЭУ

Версия: `1.0`  
Дата: `29.04.2026`

## 1. Общие сведения

### 1.1. Наименование системы

Локальная информационная система учета медицинских справок студентов кафедры физической культуры РЭУ.

### 1.2. Основание для разработки

Основанием для разработки являются:

- описание проблемы со стороны кафедры физической культуры;
- предоставленный документ с исходными требованиями;
- согласованные уточнения по составу первой версии системы.

### 1.3. Назначение системы

Система предназначена для централизованного ведения учета медицинских справок студентов, обучающихся и посещающих занятия кафедры физической культуры, с возможностью быстрого поиска, просмотра сроков действия справок, ограничений и истории изменений.

### 1.4. Цель создания системы

Создаваемая система должна:

- заменить разрозненный бумажный учет справок;
- исключить потерю информации при передаче справок между преподавателями;
- обеспечить единый доступ преподавателей к актуальным данным;
- сократить время поиска информации по конкретному студенту;
- обеспечить прозрачность изменений записей.

## 2. Объект автоматизации

Автоматизации подлежит процесс учета медицинских справок студентов кафедры физической культуры, включая:

- ведение карточек студентов;
- регистрацию данных по медицинским справкам;
- хранение истории ранее действовавших справок;
- фильтрацию и поиск по данным студентов;
- контроль сроков действия справок;
- фиксацию действий пользователей в журнале изменений.

## 3. Формат реализации системы

- Система реализуется в формате `локального веб-приложения`.
- Приложение размещается на компьютере или сервере университета.
- Доступ пользователей осуществляется через браузер по внутренней сети университета.
- Установка отдельного desktop-приложения на каждый компьютер не требуется.
- Работа через глобальную сеть Интернет не является обязательной.

## 4. Пользователи системы

### 4.1. Основные пользователи

Основными пользователями системы являются преподаватели кафедры физической культуры.

### 4.2. Права пользователей

Все авторизованные пользователи первой версии системы имеют одинаковый набор прав:

- вход в систему по логину и паролю;
- просмотр общего реестра записей;
- поиск и фильтрация записей;
- добавление новых записей;
- редактирование существующих записей;
- просмотр истории изменений.

### 4.3. Дополнительный доступ

При необходимости доступ может быть предоставлен иным уполномоченным лицам по отдельной учетной записи.

## 5. Границы первой версии системы

В состав первой версии системы входят только функции, необходимые для запуска рабочего процесса учета справок на кафедре.

### 5.1. В первую версию входят

- ведение единого электронного реестра;
- хранение карточек студентов;
- хранение информации по медицинским справкам;
- поиск по ФИО;
- фильтрация по подразделению, курсу, группе, преподавателю и статусу;
- журнал изменений;
- импорт справочных данных из Excel;
- экспорт списка в Excel.

### 5.2. В первую версию не входят

- загрузка справок студентами;
- хранение сканов и фотографий справок;
- автоматическое распознавание текста, печатей и подписей;
- мобильное приложение;
- интеграция с внешними системами университета;
- сложная ролевая модель с разделением на администратора, оператора и руководителя подразделения.

## 6. Функциональные требования

### 6.1. Авторизация

Система должна обеспечивать:

- вход пользователя по логину и паролю;
- отказ в доступе при неверных учетных данных;
- хранение данных только для авторизованных пользователей.

### 6.2. Реестр справок

Система должна обеспечивать отображение общего реестра студентов и их медицинских справок.

В реестре должны отображаться:

- ФИО студента;
- учебное подразделение;
- курс;
- группа;
- преподаватель;
- группа здоровья;
- физическая группа здоровья;
- дата начала действия справки;
- дата окончания действия справки;
- ограничения;
- статус справки.

### 6.3. Поиск и фильтрация

Система должна обеспечивать:

- быстрый поиск по ФИО студента;
- фильтрацию по учебному подразделению;
- фильтрацию по курсу;
- фильтрацию по группе;
- фильтрацию по преподавателю;
- фильтрацию по статусу справки.

### 6.4. Карточка студента

Для каждого студента в системе должна существовать карточка, содержащая:

- ФИО;
- учебное подразделение;
- курс;
- группу;
- преподавателя;
- текущую медицинскую справку;
- историю предыдущих справок.

### 6.5. Ведение справок

Система должна обеспечивать:

- добавление новой справки студенту;
- редактирование существующей справки;
- хранение нескольких справок у одного студента;
- разделение текущих и архивных справок по сроку действия.

### 6.6. История изменений

Система должна вести журнал изменений, в котором фиксируются:

- создание записи;
- изменение записи;
- удаление записи логическим способом;
- пользователь, выполнивший действие;
- дата и время действия.

### 6.7. Импорт данных

Система должна обеспечивать загрузку данных из Excel-файлов одинакового согласованного формата.

Импорт должен использоваться для:

- загрузки списка студентов;
- загрузки учебных подразделений;
- загрузки групп;
- загрузки преподавателей.

### 6.8. Экспорт данных

Система должна обеспечивать выгрузку списка записей в формат Excel с учетом примененных фильтров.

## 7. Состав хранимых данных

### 7.1. Данные по студенту

По каждому студенту должны храниться:

- ФИО;
- учебное подразделение;
- курс;
- группа;
- преподаватель.

### 7.2. Данные по справке

По каждой справке должны храниться:

- дата выдачи, если указана;
- дата начала действия;
- дата окончания действия;
- группа здоровья;
- физическая группа здоровья;
- ограничения;
- комментарий.

### 7.3. Служебные данные

По каждой записи должны храниться:

- автор создания;
- дата создания;
- автор последнего изменения;
- дата последнего изменения.

## 8. Бизнес-правила

- Один студент может иметь несколько справок за разные периоды.
- Старые справки не удаляются из истории и доступны для просмотра.
- При добавлении новой справки должна сохраняться история ранее внесенных данных.
- Поиск по ФИО должен работать без необходимости вводить полное имя целиком.
- Система должна предупреждать о возможном создании дубля студента.
- Удаление записей должно выполняться логически, без безвозвратного удаления из базы в пользовательском интерфейсе.

## 9. Статусы справки

Система должна автоматически определять статус справки:

- `Активна`, если текущая дата находится внутри периода действия;
- `Истекла`, если дата окончания меньше текущей даты;
- `Будет активна`, если дата начала находится в будущем;
- `Скоро истекает`, если до даты окончания осталось заданное количество дней.

## 10. Требования к пользовательскому интерфейсу

- Интерфейс должен быть простым, понятным и удобным для пользователей разного возраста.
- Визуальная структура должна быть ориентирована на административный формат работы: левое меню, таблицы, формы ввода и карточки.
- Основной сценарий пользователя должен требовать минимального количества действий.
- Интерфейс должен корректно отображаться на стандартных офисных мониторах.

## 11. Требования к надежности и безопасности

- Доступ к системе должен быть разрешен только авторизованным пользователям.
- Пароли не должны храниться в открытом виде.
- Все изменения данных должны фиксироваться.
- Система должна обеспечивать сохранность данных в общей централизованной базе.
- Должно быть предусмотрено резервное копирование базы данных.

## 12. Требования к размещению и эксплуатации

- Система размещается на компьютере или сервере университета.
- База данных размещается на том же оборудовании либо на выделенном внутреннем сервере.
- Пользователи работают с системой через браузер по локальной сети.
- Должен быть предусмотрен механизм резервного копирования данных не реже одного раза в сутки.

## 13. Приемочные критерии

Система считается соответствующей требованиям, если:

- пользователь может войти в систему по логину и паролю;
- пользователь может найти студента по ФИО;
- пользователь может отфильтровать список по подразделению, курсу, группе и преподавателю;
- пользователь может создать карточку студента;
- пользователь может добавить и отредактировать справку;
- пользователь может увидеть текущие и архивные справки студента;
- пользователь может просмотреть историю изменений;
- пользователь может импортировать данные из Excel;
- пользователь может экспортировать список в Excel;
- внесенные данные доступны другим авторизованным пользователям.

## 14. Этапы выполнения работ

Разработка системы рекомендуется в следующем порядке:

- согласование окончательного формата входных Excel-файлов;
- согласование состава полей карточки студента и карточки справки;
- проектирование базы данных;
- проектирование интерфейсов;
- разработка первой версии системы;
- тестирование на рабочих сценариях кафедры;
- ввод в эксплуатацию.

## 15. Результат разработки

Результатом разработки должна стать функционирующая локальная информационная система учета медицинских справок студентов кафедры физической культуры РЭУ, готовая к размещению на оборудовании университета и использованию преподавателями в ежедневной работе.
